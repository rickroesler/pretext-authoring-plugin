# PreTeXtBook org survey: nuggets from the other 13 repos

## 0. Scope and method

Ticket [#21](https://github.com/rickroesler/pretext-authoring-plugin/issues/21) asks what the
public repos in the [PreTeXtBook GitHub org](https://github.com/orgs/PreTeXtBook/repositories),
beyond `pretext` and `pretext-cli`, contribute to the plugin design. Confirmed via
`gh api orgs/PreTeXtBook/repos --paginate` and a `search/repositories?q=org:PreTeXtBook+archived:true`
check: the org has exactly **15 non-archived public repos and zero archived ones** — nothing
hidden or superseded-and-archived to add.

Method: `gh api repos/PreTeXtBook/<repo>` for metadata, `gh api .../readme` and `.../license`,
`gh api .../contributors` for maintainers, and `git clone --depth 1` into the gitignored
`scratch/org-survey/` for anything worth grepping in full. For `pretext` and `pretext-cli`,
only material **not already** in `github-issues-survey.md`, `feedback-loop-inventory.md`,
`conversion-landscape.md`, and `licensing.md` is reported here.

## 2. Tooling to integrate with rather than duplicate

**`pretext-tools` (the VS Code extension, `oscarlevin.pretext-tools`) is the load-bearing
answer here.** It is a 13-package npm workspace monorepo, not a simple snippets extension, and
several of its packages are standalone libraries usable outside VS Code:

- **Snippets** — `packages/vscode-extension/snippets/` ships ~275 snippets across five files
  covering essentially the entire PreTeXt vocabulary: every block element
  ([`pretext-elements.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/pretext-elements.json),
  117 entries — `example`, `exercise`, `webwork`, `latex-image`, `sidebyside`, all theorem-likes,
  tables, `task`, `algorithm`…), divisions and math
  ([`pretext.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/pretext.json),
  79 entries, with auto-slugifying `xml:id` generation from the typed title), attribute snippets
  ([`pretext-attributes.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/pretext-attributes.json),
  [`projectPtx-attributes.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/projectPtx-attributes.json)),
  inline markup
  ([`pretext-inline.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/pretext-inline.json),
  41), and whole-document templates
  ([`pretext-templates.json`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/snippets/pretext-templates.json),
  15 — book/article/chapter/worksheet/handout/slideshow starters).
  **Do not build a competing snippet library.**
- **Schema-driven completion and validation** — `@pretextbook/schema` compiles the official
  RelaxNG (`.rng`) schemas to JSON via `salve-annos`, is `xi:include`-aware, and drives true
  content-model-aware completions through `walker.possible()` (only offers what the grammar
  actually permits at the cursor — see
  [`packages/schema/src/completions.ts`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/schema/src/completions.ts)).
  It also has a small rule layer
  ([`packages/schema/src/rules.ts`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/schema/src/rules.ts))
  that rewrites raw errors into friendlier prose and flags one deprecation
  (`<me>` → `<md>`). It distinguishes three schemas by filename/root element: source `.ptx`,
  `project.ptx`, `publication.ptx` — any tool inspecting "a `.ptx` file" must replicate that
  disambiguation. **`@pretextbook/schema` and `@pretextbook/completions` are plain npm
  packages with no VS Code dependency** — if the plugin ever needs schema-aware
  linting/completion outside `pretext validate`, depend on these libraries rather than
  reimplementing RelaxNG-to-completions logic.
- **LSP server** — a full custom language server
  (`packages/vscode-extension/src/lsp-server/`) providing hover, symbols, `xi:include`-following
  document links, and diagnostics. Don't build a competing one.
- **Live preview / rendering** — `@pretextbook/pretext-html` runs the *official* vendored
  PreTeXt XSL stylesheets through WebAssembly (libxslt-wasm) for sub-second, no-Python preview
  with two-way source/output sync. The plugin should never attempt to reimplement PreTeXt
  rendering; defer entirely to `pretext build`/`pretext view` or this extension's preview.
- **Formatter** — `@pretextbook/format` is a standalone, configurable pretty-printer
  (`breakLines`, `breakSentences`, `breakLongAttributes`, `printWidth`) with its own CLI
  (`pretext-format --write/--check`), usable outside VS Code via `npx pretext-format`. Don't
  build a competing formatter.
- **Import wizard** — `@pretextbook/import` + `@pretextbook/latex-pretext` +
  `@pretextbook/remark-pretext` is an actively developed LaTeX/Markdown/Pandoc → PreTeXt
  converter with its own cleanup rules and preview-before-write UI (see
  `docs/latex-clean-and-split-blueprint.md` in that repo for ongoing design work). This
  corroborates and extends `conversion-landscape.md`'s finding that conversion is a live,
  contested surface — the plugin should point users at this wizard rather than write its own
  LaTeX/Markdown parser.
- **Visual (WYSIWYG) editor** — `@pretextbook/visual-editor` (React/TipTap/ProseMirror),
  experimental but substantial. Out of scope to duplicate.
- **Commands the plugin should know about, not shadow** — 30 registered VS Code commands
  including `new`, `importProject`, `buildAny/Last/File`, `view`/`livePreview`/`instantPreview`,
  `generate`, `deploy` (shells to `pretext deploy`), `format`, `spellCheck` (defers to the
  Code Spell Checker extension), `installSage`, and a `gettingStarted` walkthrough.

**Gaps `pretext-tools` leaves wide open** (where the plugin adds real value, not overlap):
no pedagogical or prose-quality review (e.g. "this `<exercise>` has no `<hint>` or
`<solution>`", notation consistency across chapters); the schema's deprecation-rule layer is
just one rule deep; WeBWorK/Sage support is a bare empty-tag snippet, with no `.pg`-syntax
completion or problem-bank browsing. These map directly onto the plugin's conventions/lint and
discipline-pack components.

## 3. Nuggets for the environment doctor

`pretext-codespace` and `pretext-docker` are both very actively maintained (both pushed within
the last week) and are **version-coupled 1:1** — the codespace template's
[`.devcontainer/devcontainer.json`](https://github.com/PreTeXtBook/pretext-codespace/blob/main/.devcontainer/devcontainer.json)
pins `pretextbook/pretext-full:<version>` to match `pretext-docker`'s
[`version.txt`](https://github.com/PreTeXtBook/pretext-docker/blob/main/version.txt), and both
are driven by Oscar Levin. Treat a mismatch between a user's pinned devcontainer tag and the
latest published tag as an environment-doctor staleness signal. Neither repo is stale or worth
steering authors away from.

Concrete, checkable facts an environment doctor can use, from
[`pretext-docker/base/Dockerfile`](https://github.com/PreTeXtBook/pretext-docker/blob/main/base/Dockerfile)
and [`full/Dockerfile`](https://github.com/PreTeXtBook/pretext-docker/blob/main/full/Dockerfile):

- **Base OS**: `debian:13-slim`. **Python**: system `python3`/`pip`/`venv` via apt, then a
  **dedicated venv at `/opt/venv`** put first on `PATH` — a doctor should check for/recreate an
  analogous venv rather than installing `pretext-cli` into system Python (this matches the
  map's own `.venv/` convention).
- **Install command**: `pip install pretext[all] codechat-server --prefer-binary --no-cache-dir`
  — note the `[all]` extras marker (pulls in PreFigure etc.), not bare `pip install pretext`.
- **Node**: pinned to `NODE_MAJOR=22` via the official NodeSource apt repo (not nvm). Note
  `pretext-tools`'s live-preview WASM (WebAssembly) path separately requires **Node 24+**
  (JSPI/`--experimental-wasm-jspi`) — a version mismatch between the CLI's own Docker image and
  what the VS Code extension needs is a real doctor-worthy check.
- **LaTeX**: **TinyTeX**, not texlive-full, then a curated `tlmgr install` list of 70+ packages
  (asymptote, beamer, pgfplots, physics, siunitx, tikz-cd, xfrac, etc.) — the closest thing to a
  canonical LaTeX-completeness manifest for PreTeXt PDF/TikZ builds, worth mirroring verbatim in
  a doctor check.
- **`jing`**: installed via plain apt package, added specifically (per the CHANGELOG) "to use
  new `pretext validate` command" — confirms `jing` is a hard prerequisite for
  `pretext validate`, not optional, corroborating `feedback-loop-inventory.md`.
- **Braille**: `python3-louis` wired into both system Python and the venv via a manual `.pth`
  file — a nonstandard step worth a doctor check if braille features misbehave in a venv.
- **Mermaid diagrams**: require `npm install @mermaid-js/mermaid-cli -g`.
- **PreFigure**: needs `prefig init` run once after install.
- **Playwright/Chromium** (needed by `codechat-server`): a specific apt lib list
  (`libnspr4 libnss3 libdbus-1-3 libatk1.0-0 …`) a Linux doctor check should verify.
- **Locale**: explicitly forces `en_US.UTF-8` — a plausible root cause for encoding-related
  build failures on minimal Linux hosts that a doctor could check.
- **Asymptote** (full image only): built from source (pinned `ASYMPTOTE_VERSION="3.13"`) for
  Vulkan-based 3D rendering, with `LIBGL_ALWAYS_SOFTWARE=1`/`XDG_RUNTIME_DIR=/tmp` since
  CI/Codespaces containers have no GPU — the single most fragile part of the toolchain; the
  repo's own README verification recipe (`asy -version` should list "Vulkan" under ENABLED
  OPTIONS) is a ready-made doctor self-test, alongside a Sage smoke test
  (`sage -c "print(factor(2024))"` → `2^3 * 11 * 23`).
- **`pretext-docker/CHANGELOG.md`** maps specific dates/versions to package additions (jing,
  `footnotehyper`, `fop`+`ghostscript` for XSL-FO PDF, `qrcode`, beamer) — a candidate source for
  a "minimum `pretext-cli` version needs package X" lookup table.
- **`pretext-codespace`'s `postCreateCommand`** installs pandoc from a GitHub-released `.deb`
  (arch-aware) rather than apt/pip — pandoc is *not* in the base Docker image at all, so a local
  (non-Docker) doctor must check for it separately. It also recommends four VS Code extensions
  (`oscarlevin.pretext-tools`, Code Spell Checker, a LaTeX table editor, a PDF viewer) — a
  checklist for an editor-extension doctor check.

## 4. Onboarding narrative and community norms (from PreTeXt-website)

- The new pretextbook.org (rebuilt in PreTeXt itself) has **no standalone FAQ page** — the old
  one ([`old_site/faq.html`](https://github.com/PreTeXtBook/PreTeXt-website/blob/main/old_site/faq.html))
  just redirected to the Guide's own Author's/Publisher's FAQ, i.e. FAQ content lives inside
  `pretext`, not the website.
- **Onboarding path** (homepage → [Why PreTeXt](https://github.com/PreTeXtBook/PreTeXt-website/blob/main/site/pages/why-pretext.md)
  → [Quick Start](https://github.com/PreTeXtBook/PreTeXt-website/blob/main/site/pages/quick-start.md)
  → [Get Help](https://github.com/PreTeXtBook/PreTeXt-website/blob/main/site/pages/support.md)):
  the recommended easiest path is **pretext.plus/tryit**, a zero-install browser editor, *before*
  GitHub Codespaces, *before* local install — a newcomer-track ordering the plugin's own
  onboarding skill should probably mirror or at least acknowledge (the plugin is squarely
  targeting the "local install" tier of this ladder).
- **Why PreTeXt page** is good seed copy for onboarding narrative: accessibility (automatic
  Braille/HTML), instructor features, "Write Once, Read Anywhere", open-source/community-driven.
- **Support page** states the community norm explicitly: "GitHub issues are reserved for
  confirmed bugs... discussed on Google Groups" first — channels are `pretext-support`,
  `pretext-announce`, `pretext-dev`, `pretext-a11y` (Google Groups), a Discord, Zoom office
  hours, and Bluesky `#PreTeXtGang`. The plugin should respect this norm if it ever
  suggests filing an issue vs. asking on a list.
- No AI/LLM (large language model) mentions anywhere in the website repo.

## 5. Templates and packs: evidence from pretext-projects, examples/, and a11y

### 5.1 pretext-projects — what real books actually look like

Live, PR-driven catalogue of 76 real projects, one XML entry per book validated against a
documented [model schema](https://github.com/PreTeXtBook/pretext-projects/blob/master/doc/model-project-entry.xml).
It tracks bibliographic/discovery metadata only — **no chapter/section/page counts**, so it
cannot answer "how big does a real book get," only what genres and features are used:

- **Subject distribution confirms math-first is right, but physics has zero real entries**:
  `math` 62/76 (82%), then `doc` 3, `misc` 2, `expository` 2, `engr` 2, `cs` 2, `writing` 1,
  `music` 1 — and **no project currently uses `subject="physics"`**, even though the schema's own
  comment anticipates it as a category. Physics-pack-second is a bet on an underserved category,
  not a proven-demand one. Closest physics-adjacent example:
  [`src/baker-statics.xml`](https://github.com/PreTeXtBook/pretext-projects/blob/master/src/baker-statics.xml).
- **Level/phase/license**: `ugld` (lower-division) 46, `ugud` (upper-division) 22; `mature` 38
  phase, `ready` 22; licence `CC` 44, `GFDL` 21 — templates should default to open licensing and
  target lower/upper-division undergraduates.
- **Feature usage (yes-flags across 76 projects)** directly ranks integration priority:
  `solutions` 33, `answers` 27, `hints` 24, **`webwork` 11** (a real, non-trivial integration
  worth a template), `projects` 9, `videos` 8, `worksheets` 5, `accessible` (self-flagged) only 3.
  **No `Runestone` or "interactive figure" field exists in the schema at all** — those
  integrations only surface via free-text description grepping (~19/76 files mention them, e.g.
  [`src/judson-AATA.xml`](https://github.com/PreTeXtBook/pretext-projects/blob/master/src/judson-AATA.xml),
  [`src/boelkins-APC.xml`](https://github.com/PreTeXtBook/pretext-projects/blob/master/src/boelkins-APC.xml)),
  meaning real authors do use Runestone but the org's own catalogue undercounts it structurally.

### 5.2 pretext repo's examples/ — an inventory for template selection

Not previously inventoried in `conversion-landscape.md`/`github-issues-survey.md`. 20 top-level
example projects (README at
[`examples/README.md`](https://github.com/PreTeXtBook/pretext/blob/master/examples/README.md);
recall `licensing.md` already flags this whole tree as GPL-licensed, so treat as reference, not
copy-paste source):

| Example | Genre/subject | Template-worthiness |
|---|---|---|
| `sample-book` | Book (abstract algebra, forked from Judson) | Best known-good book template (structural/decorative variants + annotated version) |
| `hello-world` | Bare-minimum article | Best empty-template candidate |
| `minimal` | Short article | Minimal starting template; also the designated bug-repro sandbox |
| `sample-article` | Article, deliberately every feature | Feature reference, not a clean template |
| `webwork` | Book chapter with WeBWorK problems | Good auto-graded-exercise template |
| `letter`, `memo` | Short-document genres | Good small genre templates |
| `humanities` | Non-STEM exhibits | Only non-STEM genre example |
| `errors` | Deliberately broken document | Useful as a "known-bad" validation fixture, not a template |

| `braille`, `fonts`, `pug`, `stack`, `showcase`, `workbook`, `pdf-fo-development` | Narrow/feature-testing | Not general templates |

### 5.3 a11y — dead repo, live methodology

Dormant since March 2021 (Rob Beezer solo, 20 commits), MIT-licensed, and its own BRF outputs are
now stale relative to current MathJax/SRE (Speech Rule Engine) versions — **do not treat its
outputs as current ground truth**. But it holds two things not covered in
`review-criteria.md` (which only discusses braille as an authoring-practice concern):

- **Reference documents**: the actual *Nemeth Braille Code for Mathematics, 1972* spec and
  *Braille Formats 2016* PDF, mirrored in
  [`resources/`](https://github.com/PreTeXtBook/a11y/tree/master/resources).
- **A snapshot-testing methodology worth adopting**: four curated math-expression corpora
  (source real books, 84–201 expressions each) in
  [`tests/`](https://github.com/PreTeXtBook/a11y/tree/master/tests), each with dated
  `.brf` outputs labeled by MathJax+SRE version — i.e. "does this expression still convert to
  correct Nemeth braille after an SRE upgrade" as regression testing. If the plugin ever ships an
  accessibility-pack braille check, this is the pattern to reuse (curated corpus + version-tagged
  golden outputs), even though this specific repo's own artifacts are stale.

## 6. pretext / pretext-cli deltas (not already in existing research)

- **CONTRIBUTING.md**: `pretext` has one
  ([`CONTRIBUTING.md`](https://github.com/PreTeXtBook/pretext/blob/master/CONTRIBUTING.md)) —
  discussion starts on the `pretext-dev` Google Group *before* an issue/PR, strict rebase-only
  workflow (never merge `master` into a topic branch), one branch per topic, small PRs, bug
  reports should reproduce against `examples/minimal` first. **`pretext-cli` has no
  CONTRIBUTING.md.** Relevant to the map's own eventual upstream-recommendation and
  org-handoff plans: expect a Google-Groups-first, rebase-not-merge culture.
- **`pretext-cli/docs/`** (separate from the Guide): `core_development.md` (dev-linking the CLI
  against a local core checkout), `asset-generation.md` (per-target asset cache design — content
  hash per `asymptote`/`latex-image`/`prefigure`/`sageplot` asset in `.cache/[target]_assets.json`,
  exact `-g`/`-q`/`generate -f`/`--clean` semantics), `api.md` (using `pretext-cli` as a Python
  library via `Project.parse()`/`Project()+new_target()`).
- **`pretext/doc/guide/developer/`**: developer-facing XML sources separate from the built Guide
  — `coding.xml`, `code-style.xml`, `debugging.xml`, `git.xml`, `css.xml`, `messaging.xml`,
  `localization.xml`, `pretext-script.xml`, `xsltproc.xml`. Also `doc/quickref/` (printable
  CLI/PreTeXt quick-reference LaTeX sources) and `doc/pretext-fo-roadmap.md` (XSL-FO/PDF-UA
  accessible-PDF backend roadmap).
- **GitHub Actions**: `pretext` core has **no `.github/` directory at all** — all CI/CD lives in
  `pretext-cli`. Its
  [`tests.yml`](https://github.com/PreTeXtBook/pretext-cli/blob/main/.github/workflows/tests.yml)
  is a 4-stage reusable pipeline (format/type lint → full pytest inside the
  `pretextbook/pretext-full` container → a Python 3.10–3.13 × ubuntu/windows matrix → a schema
  gate that trang-syncs RNC/RNG and jing-validates every shipped template's `project.ptx`) — a
  good pattern to mirror if the plugin ships its own template set (validity-gate the templates in
  CI). `deploy-stable.yml` cascades a release via `repository_dispatch` to `pretext-docker` and
  `html-static` (confirming the release-provenance chain in §8);
  `codespace-template.yml` regenerates `pretext-codespace` automatically on every stable release
  (so the environment-doctor's "known-good" source stays fresh without manual sync).
- **New AI/LLM mentions** beyond the already-documented origin thread:
  [`doc/guide/publisher/text-markdown.xml`](https://github.com/PreTeXtBook/pretext/blob/master/doc/guide/publisher/text-markdown.xml)
  states the Guide's own rationale for the Markdown *output* target: "Markdown is also the native
  language of AI assistants and their tools: a compact, faithful rendering of your book... is
  exactly the right thing to place in front of such a tool." This is a concrete, citable design
  input for how the plugin should feed book context to Claude — build/consume the Markdown output
  target for large-context operations rather than raw PreTeXt XML. (The `-M terse` "AI agent"
  framing in `schema-install.xml` is already covered in `feedback-loop-inventory.md` §3.3.)

## 7. Abandoned/superseded repos — steer authors away from these

- **CSS_core** and **JS_core** are explicitly self-declared obsolete: each README states the
  content "is now in the main PreTeXt repository." Anyone finding these via search should be
  pointed at `pretext` instead.
- **JS_lib**: an inert vendored-dependency dump (jQuery, knowl.js, mathjaxknowl.js), single
  contributor, no README/licence — not superseded so much as never a standalone concern; the
  plugin has no reason to reference it directly.
- **Enhancements**: one file (`trails.js`), one commit, no README/licence, last touched 2018 —
  an abandoned experiment.
- **community**: not formally deprecated, but functionally dead since July 2024 (3 commits, its
  own stated intent — "a hub for the PreTeXt community" — never materialized beyond one
  workshop's notes file, [`Day1Notes.md`](https://github.com/PreTeXtBook/community/blob/main/Day1Notes.md)).
  Its wishlist is still useful as demand evidence (§7.1 below); the repo itself is not a place to
  point authors for guidance.
- **a11y**: dormant since 2021 (§5.3) — its outputs are stale, but the repo isn't wrong so much
  as frozen; don't point authors here for current accessibility guidance (that's the Guide +
  `pretext-validation-plus.xsl`, per `review-criteria.md`), but its methodology is worth mining.
- **PROSE**: mostly "info coming soon" stub content — low information density, not dead but not
  yet useful either.

### 7.1 The `community` wishlist as demand evidence

`Day1Notes.md`'s 27 brainstormed items are pain points/requests, not ready content, but three are
worth quoting as first-party validation for design choices already being made:

- An explicit, on-record request for exactly the kind of tool this plugin is: *"Community
  control with review... Perhaps AI to go from lite documents to pretext? ... What subset of
  LaTeX converts to PreTeXt?"* — direct community-sourced justification for an AI-assisted
  conversion/authoring aid, independent of the `pretext-dev` origin thread already in the map.
- A named request for a linter (*"Linters. Highlight sloppy markup."*) with no prior art anywhere
  in the org to draw from — confirms the plugin's conventions/lint component is filling a real,
  previously unaddressed gap, not chasing an already-solved problem.
- Repeated calls for genre-specific starter templates (worksheet, syllabus, standalone,
  slideshow) that, per §5.2, `pretext`'s own `examples/` only partially satisfies (`letter`,
  `memo`, `sample-slideshow` exist; a dedicated worksheet/syllabus template does not) — a gap the
  plugin's templates component can close.

## 8. One release-pipeline nugget (html-static)

Not a plugin-design nugget so much as a fact worth knowing if the plugin ever reasons about "which
CDN asset version matches which CLI version": `html-static`'s
[`deploy.yml`](https://github.com/PreTeXtBook/html-static/blob/main/.github/workflows/deploy.yml)
is triggered by `repository_dispatch` from `pretext-cli`'s own `deploy-stable.yml` (§6), runs
`pretext-cli`'s `scripts/copy_cdn_files.py`, commits the result, and tags it to match the CLI's
release tag — so `html-static` release tags track `pretext-cli` release tags 1:1, and a jsDelivr
URL pinned to a tag corresponds directly to a specific CLI version.

## 9. Upstream-recommendation candidates surfaced by this survey

These are additive to the map's existing upstream list (ticket #7's silent-jing/stale-log/XPath
bugs, ticket #6's project.ptx/`^Gutoref` bugs); nothing here has been filed:

1. **`publication.ptx` is validated nowhere in the toolchain** (already known from the map) —
   this survey adds no new bug here, but confirms via `pretext-tools`'s
   [`validation.ts`](https://github.com/PreTeXtBook/pretext-tools/blob/main/packages/vscode-extension/src/lsp-server/validation.ts)
   that a separate, community-maintained schema-validation implementation for exactly this file
   already exists outside the CLI — worth asking Rob/Oscar whether `pretext validate` could be
   extended to cover it using the same approach.
2. **A dedicated worksheet/syllabus/course-config template is still missing** from `pretext`'s
   own `examples/`, two years after the `community` repo's workshop notes first asked for one
   (§7.1) — a concrete, small, upstreamable contribution (or a plugin-shipped template that could
   later move upstream).
3. **The `<me>`→`<md>` deprecation-rule pattern in `@pretextbook/schema`'s rule layer** is a good
   model for "soft" convention linting on top of pure schema validity, but it's currently only
   one rule deep — if the plugin builds out a broader convention/lint layer, contributing rules
   back into `@pretextbook/schema` (rather than forking it) keeps one canonical rule set instead
   of two competing ones.
4. **Node-version mismatch** between `pretext-docker`'s pinned `NODE_MAJOR=22` and
   `pretext-tools`'s live-preview requirement of Node 24+ (JSPI) — worth flagging to Oscar Levin
   (who maintains both) as a coordination gap likely to confuse Codespace users who also install
   the VS Code extension.
