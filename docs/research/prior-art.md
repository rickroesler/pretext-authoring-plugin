## Patterns worth copying (with evidence)

1. **Validate-fix loop with a validator that names the fix, not just pass/fail.** `anthropics/skills` docx/pptx `scripts/office/validate.py` reports schema, relationship, content-type, and chart errors and states the fix for each; a `--original` flag baselines pre-existing errors in a template so the agent isn't penalized for problems it didn't cause. This is exactly Rob Beezer's ask on pretext-dev ("use `pretext validate` so Claude iterates to error-free output") — evidence it works: these are Anthropic's own production document skills, not a demo.
2. **Task-router SKILL.md + one reference file per feature area, with an explicit "don't read this unless…" gate on the rarely-needed ones.** `posit-dev/skills/quarto-authoring` is a table of ~18 one-line "Task → reference file" rows, with migration-only references explicitly marked "do NOT read these when writing new documents." This is the progressive-disclosure principle plugin-dev's own `skill-development` skill preaches, seen actually shipped by the tool vendor at scale. Directly informs how to split `skills/pretext/references/*.md` between core-always-relevant and pack/migration-only material.
3. **Build-as-validator with a hard failure mode.** TinyUSB's `build-doc` skill wraps `sphinx-build -b html docs docs/_build` with `-W` (warnings become failures) and pairs it with "regenerate, don't hand-edit" rules for derived files. `pretext validate --engine salve` plus `pretext build` (both mentioned in the map) can play the same role for PreTeXt — this is direct evidence a real, CI-gated project relies on exactly this build-as-gate mechanism.
4. **Template-first over generate-from-scratch**, seen in both `latex-document-skill` (templates for resume/thesis/poster/etc., `assets/templates/`) and `typst-claude-skill` (9 ready-to-use templates) — matches the map's existing `skills/pretext/templates/` (project.ptx, docinfo-physics.ptx, physics-chapter.ptx) and Rob's ask to "bake in ... example documents."
5. **Visual re-verification pass after building.** `docx`/`pptx` skills render output to PDF then to JPEG and re-read the images as a second check beyond schema validation — a pattern PreTeXt's HTML/PDF targets could reuse (screenshot-and-look, not just `pretext validate`).
6. **Flat "gotchas" list of silent-corruption footguns**, not narrative prose — used identically by `docx`/`pptx` (e.g., hex colors with `#`, `outEnd` on stacked bars) and `typst-claude-skill` (arrays vs. content blocks). `skills/pretext/references/08-gotchas.md` already follows this shape; worth explicitly preserving it as its own reference file in the core/pack split.
7. **Explicit versioning and provenance in a skill's own metadata** (`quarto-authoring`'s `metadata: {author, version: "1.4"}` plus "based on Quarto CLI v1.9.36" in the body) — signals the skill is a maintained artifact pinned to a tool version, relevant to the map's "handoff to PreTeXtBook org" concern and to pinning against `pretext` CLI versions.

## Anti-patterns

- **One skill, 51 trigger phrases.** `latex-document-skill`'s description crams 51 numbered "use when" cases into one frontmatter block covering resumes, invoices, mail merges, PDF form-filling, and more. It is the single most-starred example found (730), so breadth alone doesn't block adoption, but it works against Claude Code's own guidance (`plugin-dev:skill-development`: keep the description focused and specific) and against the map's stated core+pack split — a monolithic "does everything" skill is the opposite of "discipline-agnostic core + packs."
- **Thin skills with no validation and no depth see near-zero adoption.** `wangmhao/claude-skill-pdf` (Pandoc+WeasyPrint, 1 star) has no validate-fix step and relies entirely on the underlying converter not erroring — contrast with the 172k-star, 730-star, and 485-star examples, all of which have either a dedicated validator script or a deep reference/template set.
- **No skill anywhere targets a genuinely strict, machine-checked XML schema (XSD/RNG) the way PreTeXt does.** LaTeX, Typst, and Pandoc all tolerate malformed/partial output (the compiler warns and keeps going); Quarto's "schema" is YAML front-matter conventions, not RNG-validated XML. The `docx`/`pptx` skills are the closest analog (validate against OOXML schema + relationships) but even they treat validation as a post-hoc check rather than Rob's ask of driving generation itself to be schema-aware from the start. This is a real gap the pretext plugin would be filling, not one it can copy wholesale.
- **Generated/derived files edited by hand.** Not observed as an active mistake in any example, but flagged explicitly as a failure mode to avoid in TinyUSB's build-doc skill ("`docs/reference/*.rst`... are generated — don't hand-edit") — worth carrying into any PreTeXt skill guidance around `publication.ptx`-derived output or generated indices.

## Portability constraints for skill files

Sources: [Anthropic's Claude Code skills docs](https://code.claude.com/docs/en/skills), the locally bundled `plugin-dev:skill-development` / `plugin-dev:plugin-structure` skills (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/plugin-dev/skills/`), and the OpenAI Codex skills docs (`developers.openai.com/codex/skills.md` → `learn.chatgpt.com/docs/build-skills.md`), cross-checked against `agentskills.io`'s open-standard writeups and a real Codex-targeted skill in the wild (`wshobson/agents` `binary-analysis-patterns`).

**What is portable (works unchanged across Claude Code, Codex, and other adopters):**
- Directory layout: `skill-name/SKILL.md` plus optional `scripts/`, `references/`, `assets/` subdirectories — no build step, no package manager, plain Git-versioned files.
- Frontmatter: only two fields are universally required — `name` (must match the parent directory name, kebab-case, ≤64 chars) and `description` (≤1,024 chars, third-person, with concrete trigger phrases).
- Progressive disclosure itself: SKILL.md as always-loaded router, `references/*.md` loaded on demand, `scripts/*` executed without ever entering context, `assets/*` copied into output rather than read.
- The `${CLAUDE_PLUGIN_ROOT}`-style portable-path discipline generalizes as "never hardcode an absolute path to a bundled file, resolve relative to the skill's own directory" — every portable skill examined does this even without a literal Claude Code plugin wrapper.

**What is Claude-Code-only / non-portable, and must stay optional per the map's "extras, never load-bearing" rule:**
- `allowed-tools` (experimental pre-approved tool list), `model`, `disable-model-invocation`/who-invokes-this control, and any Claude Code hook/subagent/MCP integration are Claude Code features with no Codex equivalent.
- Claude Code plugin-level components — `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json` — sit *outside* the skill directory and are plugin, not skill, concepts; a portable skill cannot depend on any of them existing.
- `.claude-plugin/plugin.json` manifest, and the whole plugin auto-discovery mechanism, is Claude-Code-specific packaging around portable skills, not part of the skill format itself.

**Concrete size/format limits that differ between the two adopters and therefore bound the smallest common denominator:**
- **Codex enforces an 8 KB cap on a skill's SKILL.md body** — confirmed directly in a real Codex-targeted skill (`wshobson/agents/plugins/reverse-engineering/skills/binary-analysis-patterns/SKILL.md`): "Originally a 2047-byte section in this SKILL.md. Moved to `references/details.md` to fit Codex's 8 KB skill body cap." Claude Code's own guidance (`plugin-dev:skill-development`) recommends 1,500–2,000 words (roughly 8–12 KB of Markdown) as a *soft* target with "<5k words" as an outer bound — i.e. a skill written to Claude Code's own comfortable upper bound can already blow Codex's hard cap. **Concrete implication for the pretext skill: keep SKILL.md near the low end (~1,500 words / well under 8 KB) if it must run unmodified under Codex, and push everything else into `references/`.**
- `metadata` (arbitrary key-value map), `license`, and `compatibility` (≤500 chars) frontmatter fields are optional-but-portable per the open-standard writeups (seen in use in `posit-dev/skills/quarto-authoring`'s `metadata: {author, version}` and the `docx`/`pptx` skills' `license: Proprietary`) — safe to include, but neither Claude Code nor Codex requires them, so nothing should depend on them being read.
- No portability source specifies a hard limit on `references/`, `scripts/`, or `assets/` file sizes or count — the only enforced cap found anywhere is Codex's 8 KB *SKILL.md body only*.

## Published evaluations of LLMs writing schema-constrained markup

- **JSONSchemaBench** ([arXiv:2501.10868](https://arxiv.org/html/2501.10868v3)) — the most rigorous available benchmark for constrained structured generation (10K real-world JSON Schemas, six frameworks incl. Guidance, Outlines, XGrammar). Key findings that generalize beyond JSON: (1) frameworks that *declare* schema support often fail empirically — on one hard dataset, empirical coverage ranged 3–41% despite universal declared support, i.e. "supports the format" and "reliably produces valid instances of the format" are different claims and must be tested separately; (2) constrained decoding does not degrade output quality when done well — it *improved* downstream task accuracy in every framework tested, refuting the concern that forcing validity costs correctness; (3) coverage drops sharply with schema complexity (>90% on simple schemas, <50% on complex/deeply-nested ones) — directly relevant to PreTeXt, whose schema has significant nesting (e.g., what's legal inside `<statement>`, `<exercise>`, `<sidebyside>`).
- No equivalent large-scale benchmark exists yet for XML specifically, still less for a strict RNG/XSD-validated vocabulary like PreTeXt's or DocBook's/DITA's. Web search turned up only narrower, indirect signals: general commentary that "large and newer LLMs reliably output XML formats conforming to a given schema" for well-known schema shapes, but "unlike JSON there are no guarantees" of validity, and an explicit statement in adjacent literature that "there is no prior work that provided a module for evaluating the quality of XML files generated by LLMs" — i.e. the schema-constrained-XML evaluation space is still open. This reinforces Rob Beezer's instinct: without a project-specific validate-fix loop (`pretext validate`) baked into the skill, there is no published evidence an LLM will reliably produce schema-valid PreTeXt on its own.
