# Review criteria: what the PreTeXt community considers good authoring practice

Research for issue #9 (wayfinder map #1). Sources cited inline: the local Guide
(`vendor-pretext/doc/guide/`, built at https://pretextbook.org/doc/guide/html/),
the schema's own best-practice checker (`vendor-pretext/schema/pretext-validation-plus.xsl`),
`vendor-pretext/examples/sample-article/`, and pretext-dev/pretext-support threads
(https://groups.google.com/g/pretext-dev/). Each criterion is tagged:

- **mechanical** — a script/XPath (XML Path Language)/schema check can flag it; "how" is given.
- **LLM-judgeable** — needs reading the content and authorial intent, but a
  language model can apply the rule reliably (no ground truth needed beyond the source XML).
- **human-only** — needs domain judgment, a target reader who isn't in the room,
  or institutional context (e.g. "is this the right level for my students") that
  no automated reviewer can supply.

Guide sections are cited as `guide/<file>#<xml:id>`, relative to
`vendor-pretext/doc/guide/`.

## Accessibility

| # | Rule | Source | Tag |
|---|------|--------|-----|
| A1 | Every `<image>` must have a `<shortdescription>`/`<description>`, or be explicitly marked `decorative="yes"` — never neither. | `pretext-validation-plus.xsl` template `match="image"`, message `image-description-missing` | **mechanical** — XPath: `image[not(@decorative='yes')][not(shortdescription) or shortdescription='' ][not(description) or description='']`. This is literally the schema's own check; a plugin script can run the same test standalone. |
| A2 | A decorative image (`decorative="yes"`) must **not** also carry a `shortdescription`/`description` — dead content that may not even render. | `pretext-validation-plus.xsl`, message `image-decorative-with-description` | **mechanical** — XPath: `image[@decorative='yes'][shortdescription!='' or description!='']`. |
| A3 | `<shortdescription>` must be ≤125 characters (some screen readers truncate alt text there); plain text only, no markup, avoid quotation marks. | guide/author/topics.xml#subsec-accessibility-author-provided; enforced at `image-shortdescription-length` in `pretext-validation-plus.xsl` (warns >125) | **mechanical** — `string-length(shortdescription) > 125`; plugin can also grep for markup-looking substrings as an LLM-judgeable secondary check. |
| A4 | A `<description>` should convey what the image is *intended* to convey given its surrounding context (pedagogical purpose), not a generic visual inventory; give an overview first, then structure (left-to-right / clockwise), be concise, avoid pure visual shorthand for readers who can't see. | guide/author/topics.xml#subsec-img-desc-advice (Michael Cantino's advice, worked examples) | **LLM-judgeable** — requires reading the surrounding prose/exercise and judging whether the description matches authorial intent; a good target for an accessibility-review agent, not a script. |
| A5 | Long descriptions of tables/graphs should use `<tabular>` structure inside `<description>` (e.g. vertex/edge adjacency lists) rather than prose alone, when the content is inherently tabular. | guide/author/topics.xml#subsec-img-desc-advice (Combinatorial Graph example) | **LLM-judgeable**. |
| A6 | Don't abuse `<m>` for visual tricks (e.g. superscript "th") — confuses braille/MathJax/SRE (Speech Rule Engine, MathJax's) rendering. | guide/publisher/braille.xml (topic-braille-practices) | **LLM-judgeable** — pattern is recognizable (e.g. `<m>^{th}</m>` after a number) but judging "abuse" vs. legitimate math needs context; could seed a heuristic mechanical grep too. |
| A7 | Punctuation immediately after inline/display math must be authored in the *logically* correct position (inside vs. outside `<m>`/`<md>`) — braille/audio and print diverge otherwise. | guide/author/topics.xml#authoring-math-punctuation (referenced from accessibility chapter) | **LLM-judgeable**, borderline mechanical — a script could flag `</md>` immediately followed by `.` `,` `;` in the source for manual/LLM review, but "logically correct" needs sentence context. |
| A8 | Avoid relying on color alone to distinguish content (e.g. use strike-through + underline for delete/insert, not color only); think about black-and-white print and color-vision-deficient readers before coloring math. | guide/author/topics.xml#topic-accessibility ("Colors"), #color-in-math | **LLM-judgeable**. |
| A9 | Multi-column lists (`cols` attribute on `<ol>`/`<ul>`/`<exercisegroup>`) are purely presentational and are read cell-by-cell by a screen reader (each cell announced as its own one-item list) — prefer leaving `cols` off and let the publisher/styling decide. | guide/author/topics.xml#topic-accessibility ("Multiple Columns") | **mechanical** — XPath: any `@cols` attribute present flags for review. |
| A10 | Commutative diagrams should be authored with the `amscd` LaTeX package (inside `<md>`) rather than a general drawing tool — MathJax renders it accessibly (braille/screen-reader friendly); general drawing tools do not. | guide/author/topics.xml#commutative-diagrams, #topic-accessibility | **LLM-judgeable** (needs to recognize the diagram is commutative and check for `\begin{CD}` vs. e.g. `tikz`/asymptote). |
| A11 | `<sidebyside>` and tactile/3D content are poorly supported in braille conversion — think about whether panel content (esp. images) will make sense "unwound" into a vertical sequence; Asymptote 3-D images are more accessible (keyboard-navigable) than static raster for motor-impaired readers. | guide/publisher/braille.xml; guide/author/topics.xml#topic-braille-practices | **human-only** — requires judging the pedagogical role of the layout, not something a script or even most LLM passes can verify without rendering the braille output. |
| A12 | Video should be captioned/have a transcript for screen-reader/deaf users; avoid being "overly reliant" on video/interactive demos as the *only* carrier of information (braille/print readers get nothing). | guide/publisher/braille.xml (topic-braille-practices, "not being overly-reliant on video") — note: Guide does **not** mandate closed captions explicitly, this is inferred from WCAG (Web Content Accessibility Guidelines) cited at guide/author/topics.xml#topic-accessibility | **LLM-judgeable** for "is this video redundant with text nearby", **human-only** for "are the captions actually accurate" (needs to watch the video). |
| A13 | Links: avoid "click here" style text; give an `xref`/`url` informative content so the clickable target is large and self-describing; underline-vs-color for PDF hyperlinks is a publisher option worth turning on for colour-blind readers. | guide/author/topics.xml#subsec-accessibility-author-provided ("Link Text") | **LLM-judgeable** — mechanical pre-filter possible: grep url/xref content for "here"/"click here"/"link". |
| A14 | Tables: put footnote-like material as `<tn>` (table note), never `<fn>`, inside a `<tabular>`. | `pretext-validation-plus.xsl`, message `footnote-in-tabular` (error severity) | **mechanical** — XPath `tabular//fn`. |
| A15 | A `<tabular>`'s rows must all span the same number of columns (counting `colspan`) — a ragged tabular has unpredictable, possibly inaccessible, rendering. | `pretext-validation-plus.xsl`, message `tabular-ragged-rows` | **mechanical** — the XSLT (Extensible Stylesheet Language Transformations) already computes this per-row; reusable as a standalone XPath/script. |
| A16 | Word-processor-imported curly quotes, en/em dashes, degree/multiplication signs, and zero-width spaces should be replaced with PreTeXt's semantic elements (`<q>`, `<ndash/>`, `<mdash/>`, `<degree/>`, `<times/>`) rather than raw Unicode — affects braille/screen-reader/LaTeX fidelity. | `pretext-validation-plus.xsl`, messages `unicode-*` | **mechanical** — literal codepoint `contains()` checks per character, already implemented; trivially portable to a plugin script. |
| A17 | Divisions should be titled (even a `<remark>`) so a screen-reader/knowl user isn't left navigating anonymous "Example 5.10" clickables. | guide/author/topics.xml#best-practice-titles | **LLM-judgeable** (is a title present and informative) / **mechanical** for presence-only (grep for divisions lacking `<title>`, though schema may already require it for numbered blocks). |
| A18 | MathJax/SRE is on by default and gives audible math exploration; don't disable it or work around it with images-of-equations. | guide/author/topics.xml#topic-accessibility (Mathematics subsection) | **human-only**/**mechanical** hybrid — mechanical to detect `<image>` containing rendered equations (heuristic on caption/description text), human judgment on why. |

## Pedagogy

| # | Rule | Source | Tag |
|---|------|--------|-----|
| P1 | An `<exercise>` needs a `<statement>` wrapper as soon as it has a `<hint>`, `<answer>`, or `<solution>`; a bare question with none of those may omit `<statement>`. | guide/author/topics.xml#exercise-statement-structure | **mechanical** — schema-enforceable structurally; XPath: `exercise[hint or answer or solution][not(statement)]`. |
| P2 | Author hints/answers/solutions to an exercise *immediately following* its statement — never scattered — since visibility/relocation to a back-matter Solutions division is a rendering choice, not an authoring one. | guide/author/topics.xml#topic-exercises-solutions | **mechanical** for adjacency structurally (schema likely already enforces child order); **LLM-judgeable** for "is a hint/answer/solution missing where pedagogically expected". |
| P3 | Conceptually: `<answer>` = short final result (may have several), `<solution>` = the worked route to it; don't conflate the two. | guide/author/topics.xml#exercise-statement-structure | **LLM-judgeable** — requires reading content, not just tag names. |
| P4 | A multi-part exercise uses `<task>` (nestable up to 3 levels; a 4th level is an error), each structured like an exercise, with the parent `<exercise>` optionally framed by `<introduction>`/`<conclusion>`. | guide/author/topics.xml#exercise-tasks | **mechanical** — XPath depth-count on nested `task` > 3 is a schema violation already; reviewer can restate the reason. |
| P5 | A divisional exercise's `number` attribute (to pin stable problem numbers) should be used sparingly — once you override one, you'll usually need to set every subsequent number too; best saved for a mature/stable project. | guide/author/topics.xml#exercise-inline-divisional | **human-only** — a maturity/workflow judgment call, not verifiable from the XML alone. |
| P6 | `<exercisegroup>` needs a required `<introduction>` (shared instructions for the run of exercises), may have a `<conclusion>`, and an optional `<title>`. | guide/author/topics.xml#exercise-inline-divisional | **mechanical** — schema-checkable (`introduction` required). |
| P7 | `<worksheet>` is print-first: may open with `<objectives>` + `<introduction>`, close with `<conclusion>` + `<outcomes>`; body is one or more `<page>`; only inside a worksheet may `<exercise>` sit in a `<sidebyside>`; use `workspace` attribute for blank working room. | guide/author/topics.xml#topic-worksheet | **mechanical** for structural placement (schema-checkable); **LLM-judgeable** for whether `workspace` sizing is pedagogically reasonable. |
| P8 | `<reading-questions>` exist to check comprehension of *surrounding* material — not to introduce new content or serve as graded assessment. | guide/author/topics.xml#exercise-inline-divisional | **LLM-judgeable** — requires comparing reading-question content against the division's prose. |
| P9 | The `<solutions>` element (child of `backmatter` or a division) auto-generates a solutions appendix/subsection scoped by `scope`, filtered by `inline`/`divisional`/`reading`/`worksheet`/`project` × `statement`/`hint`/`answer`/`solution`, with an `admit="odd\|even\|all"` filter on serial number — author intent here belongs in this element's attributes, not by manually duplicating content. | guide/author/topics.xml#topic-solutions-division | **mechanical** — detect manual duplication of exercise content elsewhere in source as an anti-pattern (a grep for exercise statements repeated verbatim) — a good script-assisted check. |
| P10 | `<objectives>`/`<outcomes>` are structured lists that may only appear early (`objectives`) or late (`outcomes`) in a division/worksheet — not both anywhere, not mid-division. | guide/author/topics.xml (topic-blocks list around line 933) | **mechanical** — schema-checkable position. |
| P11 | `<introduction>`/`<conclusion>` are the standard way to frame a division's (or a multi-part exercise's, or an exercisegroup's) content — use them for scene-setting/wrap-up prose rather than ad hoc leading/trailing `<p>`. | guide/author/topics.xml#exercise-tasks; #topic-front-matter (preface ≠ introduction, see P13) | **LLM-judgeable** — style convention, not enforceable structurally beyond "does the element exist". |
| P12 | Interactive exercises (true/false, multiple choice, matching, clickable-area, fill-in, coding, short-answer) each need a `<statement>` plus a specific "signal" child (e.g. `@correct` for true/false); a static fallback (print/PDF/braille) is auto-generated from the same markup — don't hand-author a redundant static version. | guide/author/topics.xml#topic-interactive-exercises | **mechanical** — each interactive type's required-signal-child rule is a straightforward XPath the schema mostly already checks; reviewer can name which is missing. |
| P13 | A `<preface>` is not introductory content and is not an `<introduction>` — it is the author's own account of why/how the book was written (per Chicago Manual of Style); several editions' prefaces are ordered newest-first. | guide/author/topics.xml#best-practice-preface | **LLM-judgeable** — genre confusion is common and needs reading the content, not just the tag. |
| P14 | Every Runestone/WeBWorK-hosted interactive component (exercise, task, project, video, program, etc.) **must** carry a stable `label` attribute, decided *before* first hosting — changing it orphans database records/student progress; label derives from `docinfo/document-id` + `edition`. | guide/author/topics.xml#best-practice-label | **mechanical** — XPath: any Runestone-eligible interactive element lacking `@label`; also check `docinfo/document-id` exists before flagging as ready-to-host. |
| P15 | Provide `<feedback>` on interactive exercises (optional but "highly encouraged") to improve the static/automated-solution quality beyond a bare "True"/"False". | guide/author/topics.xml#topic-interactive-exercises | **mechanical** presence-check + **LLM-judgeable** quality of feedback text. |

## Consistency

| # | Rule | Source | Tag |
|---|------|--------|-----|
| C1 | Custom math notation belongs in `docinfo/macros`, one-or-two-argument, one-line definitions, named *semantically* (e.g. `\adjoint{A}`, not `\a{A}`) so the definition can change without touching every use. | guide/author/topics.xml#mathematics-macros, #semantic-macros | **LLM-judgeable** — "semantic naming" and "one-line/simple" are judgment calls; **mechanical** pre-filter for macro names containing digits (which silently breaks MathJax, per the Guide) or multi-line macro bodies. |
| C2 | Macro names must not contain digits — MathJax will silently fail to read that macro and everything defined after it. | guide/author/topics.xml#mathematics-macros | **mechanical** — regex on `docinfo/macros` content for macro names matching `\\[a-zA-Z]*[0-9]`. |
| C3 | `xml:id` values must be organized/predictable but never contain embedded numbers meant to track position (e.g. don't encode "chapter 5" in the id) — ids should be readable and stable across reordering. | guide/author/topics.xml#topic-cross-referencing ("Creating a Cross-Reference" note, "Use xml:id Frequently") | **LLM-judgeable** — mechanical pre-filter possible (regex for ids ending in digits that look like numbering, e.g. `sec-5`, `thm-3-2`) flagged for human/LLM confirmation. |
| C4 | Use `xml:id` liberally — on every division and anything you might reference later; do it as you write, not retroactively. | guide/author/topics.xml#topic-cross-referencing (best-practice-label note) | **mechanical** — flag divisions/numbered blocks lacking `xml:id`; **human-only** for "liberally enough" on non-numbered content. |
| C5 | Cross-reference text style (`type-global`, `local`, `hybrid`, etc.) should be set once, document-wide, via `docinfo/defaults/xrefs/@text`, and only overridden per-`xref` when there's a real reason (e.g. "far away" vs. "close by" targets). | guide/author/topics.xml#topic-cross-referencing | **mechanical** for detecting per-xref `@text` overrides to audit against the document default; **LLM-judgeable** for "is this override justified". |
| C6 | Avoid "here"/"click here" as `xref`/`url` link text (repeated from A13) — also a consistency/style issue across the document, not just accessibility. | guide/author/topics.xml#subsec-accessibility-author-provided | **mechanical** grep. |
| C7 | Numbering: pinning a divisional exercise's `number` attribute is a one-way door — override one and you'll typically need to set every later one too; braille readers rely on hierarchical numbering depth as a structural cue, so turning off division numbering below some level has accessibility consequences too. | guide/author/topics.xml#exercise-inline-divisional; #topic-braille-practices | **human-only** for the exercise-numbering workflow tradeoff; **LLM-judgeable** for flagging a numbering-suppression choice in `publication.xml` for accessibility review. |
| C8 | `label` (Runestone/WeBWorK identifier) and `xml:id` (cross-reference identifier) are companion but distinct mechanisms — `label` is reader-facing/stable-forever (web page names, image filenames, DB (database) keys), `xml:id` is source-only. Don't conflate or reuse a value expecting the same guarantees. | guide/author/topics.xml#best-practice-label | **LLM-judgeable** — needs to check both attributes exist and serve their distinct purpose, not just presence. |
| C9 | `document-id` (in `docinfo`) must be distinctive and is meant to *never change*; `edition` may increment when labels need to be revised. Decide both before first Runestone hosting. | guide/author/topics.xml#topic-docinfo, #best-practice-label | **mechanical** presence-check; **human-only** for "is this actually stable enough" (a judgment made once, hard to verify after the fact). |
| C10 | Titles: use `<title>` liberally on every structure that allows one (even a `<remark>`); reserve `<shorttitle>`/`<plaintitle>` for genuinely long titles or markup (e.g. LaTeX commands) that breaks in a browser tab — don't use them routinely. | guide/author/topics.xml#topic-title | **mechanical** presence-check for missing titles on nameable divisions/knowl-eligible blocks; **LLM-judgeable** for "is the title actually informative" (Bad/Better/Best ladder given in the Guide). |
| C11 | A `<title>` containing `<m>` (math) should also carry a `<shorttitle>` — math renders poorly or not at all in browser tabs/ToC (Table of Contents). | `pretext-validation-plus.xsl`, message `title-math-no-shorttitle` | **mechanical** — XPath `title[m][not(following-sibling::shorttitle)]`, restricted to the listed division-parent set the XSLT names. |
| C12 | A numbered container (`figure`, `table`, `listing`, `list`) should not be nested inside an inherently unnumbered container (`assemblage`, `interactive`, `slate`, `colophon`, `headnote`, `biography`, `acknowledgement`, `preface`, or an `exercisegroup`/`reading-questions`'s `introduction`/`conclusion`) — the number becomes unreliable. | `pretext-validation-plus.xsl`, message `numbered-item-unnumbered-container` | **mechanical** — the XSLT computes the exact ancestor set; directly reusable. |
| C13 | Index entries: lower-case except proper nouns; place `<idx>` *between* sentences, not at paragraph start/end; use `<seealso>`/`<see>` correctly (a `see` cannot have its own locator, a `seealso` must); avoid double-posting errors; singular/plural should track the text's own usage. | guide/author/topics.xml#topic-index, #topic-index-advice | **mechanical** for the `see`/`seealso` locator-presence rule (already schema/XSLT-checked with a build warning); **LLM-judgeable**/**human-only** for indexing quality (this is explicitly called "a job for a skilled professional" in the Guide). |
| C14 | A `<notation>` element is best placed as metadata inside a `<definition>` (right after `<title>`), not buried in a later paragraph — the HTML build then knolws the whole definition as the locator, which is more useful than a bare-paragraph knowl. | guide/author/topics.xml#topic-notation | **LLM-judgeable** — needs to see where in the definition the notation element sits. |
| C15 | Don't hand-duplicate raster/vector image files under near-identical `xml:id`s (e.g. `-copy-2`) without a real reason — each copy needs a unique `xml:id` and duplicates content maintenance burden. | guide/author/topics.xml#topic-images-vector (around "@copy" discussion) | **mechanical** — detect duplicate `@source` values across distinct `<image>` elements. |
| C16 | `\text{}` is the only sanctioned way to put regular text inside math — never `\mbox{}`, never font-changing commands (`\rm`); no math inside `\text{}`; do include the surrounding spaces inside `\text{}`. | guide/author/topics.xml#text-in-mathematics | **mechanical** — regex in `<m>`/`<md>`/`<mrow>` content for `\mbox{` or bare font-switch commands. |
| C17 | Never author a LaTeX *display* environment (`align`, `gather`, `equation`) directly inside `<m>`/`<md>`/`<mrow>` — PreTeXt chooses the environment; only matrix/`cases` environments are legitimate inside a formula. | guide/author/topics.xml#cases-and-matrices | **mechanical** — regex for `\begin{align}`/`\begin{gather}`/`\begin{equation}` inside math elements (schema likely already rejects some of this, but not all, since it's raw LaTeX text). |
| C18 | Deprecated markup should not appear in new/edited content: `@filebase` (→ `xml:id`), `<cite>` (→ `xref`), `<circum>` (→ `circumflex`), `sage/@copy`, `image/@copy`. | `pretext-validation-plus.xsl`, `deprecated-*` messages | **mechanical** — direct reuse of the existing XSLT templates; this is literally what `pretext validate`-adjacent tooling already flags. |

## Contested / where the community disagrees

- **Alt text for interactive/embedded diagrams (Asymptote, iframes).** A 2025 pretext-dev thread (Sean Fitzpatrick, "Image Descriptions for Asymptote Diagrams") shows there's no settled answer for how to attach a good text alternative when the "image" is actually an interactive WebGL (Web Graphics Library)/iframe object rather than a static raster — the Guide's `shortdescription`/`description` model was designed for static images first.
- **Tabbing/navigation depth vs. content collapse.** Threads on "Icon for Long Description" (2024) and "Styling of WeBWorK Parts" (2020) surface an unresolved tension between hiding content behind knowls (good for reducing tab-stops per the Guide's own "Skip to Main Content" rationale) and screen-reader users needing to reach nested content without excessive tabbing — no single answer, and it interacts with publisher-level knowl settings, not just authoring choices.
- **Container/structure placement for pedagogical framing.** A "Design Discussion, 2D containers" thread asks, open-endedly, whether shared instructional text belongs at `worksheet`, `worksheet/page`, or `worksheet/introduction`, and similarly for `exercisegroup/introduction` vs. `reading-questions/introduction` — i.e. even PreTeXt's own maintainers are still settling *where* certain pedagogy-adjacent content should live, which matters for any review agent trying to enforce "put the shared context in the right container."
- **How strict to be about `xml:id`/`label` naming conventions.** The Guide is emphatic ("don't use numbers", "keep them readable") but is descriptive, not prescriptive, about a naming *scheme* — there's no single blessed convention (e.g. `sec-topic` vs. `topic-sec` vs. discipline-prefixed), so a consistency-reviewer agent enforcing one scheme would be imposing a house style, not a community consensus.
- **125-character alt-text limit.** The Guide itself calls the exact character limit "a matter of some debate" among screen readers, even while the schema's own `pretext-validation-plus.xsl` hard-codes 125 as the warning threshold — so the mechanical check exists, but the community doesn't agree it's the right number.
- **Braille/tactile-graphics support for `sidebyside` and 3D images** is explicitly called out as unfinished/unresolved in the Guide (braille.xml, 2022-11-30 note) — not a disagreement so much as an acknowledged gap a reviewer should not pretend has a settled best practice.

## Summary for the map

Best PreTeXt-authoring practice is mostly captured in three tiers: a strict,
already-XPath-implemented mechanical layer (the community's own
`pretext-validation-plus.xsl` — image descriptions, tabular shape, deprecated
markup, Unicode substitutions, title/shortitle pairing, label presence for
Runestone/WeBWorK), a large LLM-judgeable layer (does an image description
match authorial intent, is a title actually informative, is a `<preface>`
being used as an introduction), and a small human-only layer (braille/tactile
support gaps, numbering-workflow tradeoffs, index quality) that the Guide
itself says needs a skilled professional or is still unsettled upstream.
