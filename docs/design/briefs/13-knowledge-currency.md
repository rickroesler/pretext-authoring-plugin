# Brief 13 — Knowledge-currency strategy: how the plugin tracks PreTeXt changes

Ticket: [#13](https://github.com/rickroesler/pretext-authoring-plugin/issues/13). Status: **for grilling, not decided.**

## 1. The question

PreTeXt's schema and CLI change continuously. How does the plugin stay correct: vendor a pinned
snapshot and regenerate references from it; fetch live at use time; read the *installed* `pretext`
and its bundled schema; or have upstream host the skill? What does each cost in tokens, latency,
staleness and maintenance, and which fits the PreTeXtBook-org handoff?

## 2. Evidence

- **pretext-dev-survey.md (a)** — ~one `[CHANGE]`/`[DEPRECATE]`/`[NEW]` notice **every 1–2 weeks**
  (dozens/year), "but the actual breakage rate for markup an author wrote a year ago is **low**;
  almost every change ships with a deprecation warning and a working fallback" (the 2026-07-31
  `docinfo/cross-references/@text` → `docinfo/defaults/xrefs/@text` migration is the model).
- **pretext-dev-survey.md (d) + caveat** — hard breaks are confined to `experimental-features.xml`
  ("among the most likely parts of PreTeXt to change"); and that file "is generated by diffing two
  RELAX-NG grammars in the *current* clone … treat it as 'the list to check before every release'."
- **feedback-loop-inventory.md §7** — the authoritative schema is already on the author's machine at
  `~/.ptx/<version>/core/schema/`, version-locked to the installed CLI; a 52-line `lxml` query
  answers "what may go inside X" in **0.03 s**, offline, and the dev-vs-production diff *is* the
  definition of experimental. Two traps for a reimplementer: `pretext-dev.rng` is
  `<include href="pretext.rng"/>` plus additions, and `combine="choice"` means union, not override.
- **feedback-loop-inventory.md §3.4, §9** — jing's contextual "expected element …" list is "strictly
  better than any static schema lookup", i.e. the freshest knowledge source is the installed
  validator itself, not any document we ship.
- **github-issues-survey.md §4** — validation internals are mid-refactor (pretext#3004/#3027/#3033,
  cli#1189 open): "the CLI-facing `pretext validate` contract (exit codes, `--report-form terse`) looks
  stable and is the right integration surface; don't couple to `pretext.py` internals." Also: braille
  is being re-architected; MathJax 4 migration is open since 2022; Codespaces templates get rewritten.
- **github-issues-survey.md, Docs gaps** — pretext#1970 (Guide said images go in root/`images`,
  actually `external/`), pretext#2626 (tutorial drifted from the Codespace template), pretext#2141
  (devscript docs out of date) ⇒ **"bake authoritative guidance in from the current schema/examples,
  not by paraphrasing the Guide prose, which has lagged behavior before"**; and "any bundled example
  content should be periodically rebuilt/verified against the vendored `pretext` version".
- **prior-art.md, Pattern 7** — `quarto-authoring` carries `metadata: {version: "1.4"}` plus "based on
  Quarto CLI v1.9.36" in the body: a versioned, pinned, maintained artifact.
- **licensing.md §3** — Guide prose is GFDL; schema and examples are GPL; both must live in their own
  quarantined subdirectories with headers intact. ⇒ *regenerating* references from the schema is also
  the licence-cleanest route (facts, not paraphrase — §2(a)).
- **pretext-dev-survey.md (f)** — Rob Beezer: "Don't forget the schema and all of the example
  documents — I think those might help where the 'real' documentation is not so good", and he holds
  "a pile of useful rules anhd hints" not yet published.

## 3. Options

| Option | Cost | Benefit |
|---|---|---|
| **A. Vendor a pinned snapshot; regenerate references from it.** | A release cadence to maintain (~monthly given the churn rate); GPL/GFDL quarantine work; staleness between releases. | Deterministic, offline, reviewable, cites a version like `quarto-authoring`; zero latency/tokens at use time. |
| **B. Fetch live from pretextbook.org / GitHub at use time.** | Network dependency in an authoring loop; unbounded tokens; no reproducibility; scrapes GFDL prose per use. | Never stale. |
| **C. Read the *installed* `pretext` and its bundled `~/.ptx/<version>/core/schema/`.** | Needs a working install (which the doctor already requires); answers are grammar-shaped, not prose; version skew between author machines. | Always exactly right for *that* author; 0.03 s; no shipping of GPL schema at all — it's already on their disk. |
| **D. Upstream hosts the skill, shipping with `pretext` releases.** | Not ours to decide; requires Rob's team to own a release step; blocks v0.1. | Perfect currency and the natural end-state of the handoff. |

## 4. Recommendation

**C as the runtime source of truth, A as the authored layer, D as the stated destination.**

Concretely: prose references are written **from facts** and pinned to a named CLI version in
frontmatter `metadata` (A, per prior-art Pattern 7 and the licensing recommendation to avoid
paraphrasing GFDL prose); but every *answer that the schema can give* — what may go inside an element,
what is experimental, what is deprecated — is resolved at use time against the author's own
`~/.ptx/<version>/core/schema/` and against jing's contextual "expected" list (C). This is the only
option where the plugin cannot be wrong about the version the author is actually running, and it
sidesteps redistributing GPL schema entirely.

Live fetching (B) is rejected: the churn evidence says the *risk* is not stale production markup
(deprecate-then-remove, old form keeps working) but experimental markup — and the experimental list is
derivable locally by the dev-vs-production diff, for free. What we do ship pinned is: a documented
supported-CLI-version range, a `check-currency` step that compares installed `pretext --version`
against the pinned one and warns when the author is far ahead, and a maintenance ritual of rebuilding
the bundled templates against the vendored version (pretext#2626/#1970 both being drift bugs).

**D is the handoff argument:** designing the references as regenerable-from-schema, and pinning a
version in metadata, is exactly what makes it cheap for Rob's team to adopt a release step later.

## 5. Grilling questions (defaults)

1. Ship a vendored schema copy, or always read `~/.ptx/`? *Default: always read `~/.ptx/`; ship none (also the cleanest GPL answer).*
2. What happens when `~/.ptx/` is missing or the CLI isn't installed? *Default: doctor refuses and gives install steps; the skill answers from prose references with an explicit "unverified against your version" caveat.*
3. What is the pinned baseline version for v0.1? *Default: the CLI the demo build was verified against (2.51.0), named in SKILL.md and in `metadata`.*
4. How wide a version skew before we warn? *Default: warn on any minor-version gap; hard-warn on a major.*
5. Is there an automated regeneration script for schema-derived references? *Default: yes, one script, run at release time — not at use time.*
6. Release cadence? *Default: on-demand, triggered by an `experimental-features.xml` diff or a CLI minor bump, not calendar-driven.*
7. Do we track the pretext-announce list mechanically? *Default: no — no API; a manual pre-release read of announce + `experimental-features.xml` diff.*
8. How does Rob's "pile of rules and hints" land? *Default: a dedicated `references/community-rules.md` plus a CONTRIBUTING path so he can drop a file rather than translate it into Skills format.*
9. Do references quote the Guide at all? *Default: no direct quotation; facts restated. Any file that does track Guide wording goes in `references/guide-derived/` under GFDL.*
10. Do we pin to a CLI version *range* or a point version? *Default: point version pinned, range documented as "verified 2.5x".*

## 6. Hard-to-reverse → ADR candidates

- **ADR: runtime-resolved schema knowledge vs. vendored snapshot.** Decides whether the plugin ships GPL material at all, and every schema-touching component's contract. Reversing means rewriting references and the licensing NOTICE.
- **ADR: integration surface = the `pretext` CLI contract only** (`validate` exit codes + `--report-form terse`), never `pretext.py` internals. Validation internals are mid-refactor; coupling now would be expensive to undo.
- **ADR: version pinning and declared support policy** (what "supported" means, how skew is reported) — a public compatibility promise.
